# 评测数据规格与合规说明

> 适用页面：后台管理 → 评测（`/rag/eval`）。本规格描述外部评测用例的批量导入格式、字段语义、校验规则与合规要求。系统仅做结构校验，不做语义校验；导入前请自行完成数据清洗与脱敏。

## 一、评测工作流

```text
建立评测集 → 导入/生成用例 → 选择检索开关与生成/评测模型 → 运行 → 查看指标与对比 → 复核 Bad Case → 调参回归
```

1. **建集**：在评测页新建或选择评测集
2. **备用例**：批量导入（本规格）或从文档分片生成候选用例
3. **运行**：分别以检索关闭（off）与开启（on）运行；勾选答案质量评测时，分别选择生成模型与评测模型
4. **看指标**：hit@k、MRR、Context Precision/Recall、答案关键词命中、答案正确性与裁判评分等
5. **复核**：对未命中与低分用例标注 Bad Case 类型，沉淀为回归集
6. **回归**：调整检索参数或提示词后重跑，对比前后指标

> 运行中页面会显示阶段（关闭重排检索 / 开启重排检索 / 生成并评判答案）、已处理条数与百分比；离开页面后重新进入，运行记录会自动续显进度。

## 二、字段定义

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `query` | 是 | string | 用户问题（评测输入） |
| `relevant` | 否 | string[] / string | 应命中文档标题，用于 hit@k / MRR / recall |
| `answerability` | 否 | enum | `answerable` / `unanswerable` / `unlabeled`，显式声明可答性；留空时按 `relevant` 与备注文本推断 |
| `split` | 否 | enum | `tuning`（调参）/ `regression`（默认）/ `frozen`（冻结验收），冻结集不参与调参 |
| `business_criticality` | 否 | enum | `critical` / `important` / `normal`（默认），关键用例单独统计 |
| `gt_answer` | 否 | string | 标准答案，用于答案质量评测 |
| `gt_keywords` | 否 | string[] / string | 标准答案关键词，用于关键词命中率 |
| `query_type` | 否 | enum | `fact`（默认）/ `compare` / `howto` / `policy` |
| `difficulty` | 否 | enum | `easy` / `normal`（默认）/ `hard` |
| `notes` | 否 | string | 备注、来源或预期 Bad Case 类型 |
| `source` | 否 | string | 来源标识，默认 `import`；建议填批次号/脚本名 |

## 检索模式与 Hybrid 对照

| 模式 | 含义 | 适用场景 |
|---|---|---|
| `dense` | 只开向量召回，关闭 Hybrid | 建立基线；排查向量本身问题 |
| `hybrid` | 向量 + 关键词并行召回，RRF 融合 | 生产默认推荐模式；兼顾语义与术语精确匹配 |
| `keyword_fallback` | 向量异常/空结果时的兜底 | 故障降级，**不作为正常指标**参与对比 |

> 评测运行可在「检索模式」显式选 dense/hybrid，与后台全局配置隔离，完成同环境 A/B；结果逐条会标注 `retrieval_mode` 与 `retrieval_summary`，前端「引用来源」可直接看出本次检索走的是向量、关键词还是混合。

> 若 `relevant` 与知识库文档标题不一致，不会报错，但该用例 hit@k 恒为 0，评测结果会失真。导入前务必核对标题。
>
> 兼容更细的板块标注：`家长常见540问-板块3课程体系与学习路径` 会自动归一到实际检索标题 `家长常见540问`。但前提是检索结果里出现了该文档标题；如果标注的板块属于另一篇未召回文档，仍会算未命中。
>
> 建议新批次逐步补齐 `answerability`：可答但漏标注 `relevant` 会被归入「未标注」而不计入检索指标；明确不可答的问题请标 `unanswerable`，系统会单独校验拒答率。

### 2.1 生成模型与评测模型

勾选「答案质量评测（LLM 裁判）」后，需要分别选择：

| 角色 | 作用 | 建议 |
| --- | --- | --- |
| 生成模型 | 基于检索片段生成回答，用于关键词命中与裁判评分 | 与线上客服/教学实际使用的模型保持一致 |
| 评测模型 | 对回答的忠实度、相关性、完整性、表达、逻辑打分 | 选择不同厂商或不同模型，降低同源偏好；temperature=0 |

- 两个模型必须不同（配置 ID 与模型名都不能相同），前端与后端都会校验
- 模型来自当前评测集 owner 在「设置 → 模型配置」中已配置的模型
- 只跑检索指标（hit@k / MRR / recall）时不会调用 LLM，模型选择不生效
- 每次运行会快照生成/评测模型名，历史记录可在运行表中追溯

### 2.2 不可答 / 负向用例

`relevant` 留空的用例不会参与 hit@k / MRR / recall 等命中类指标，避免把「正确拒答」误判成「检索失败」。

- 如果用例本身是「文档未提供」类问题，请在 `source` 或 `notes` 中写明 `unanswerable`，系统会单独统计为「不可答」
- 如果只是暂时没有标注应命中文档，系统会单独统计为「未标注」，建议补齐 `relevant` 后再做回归
- 答案质量评测仍会运行不可答用例，用于观察模型是否编造；结果中的 `abstention_rate` 统计明确拒答比例（出现「文档未提供 / 不知道 / 无法回答」等表达），可答用例应接近 0%，不可答用例应接近 100%
- 若怀疑大文档（如 FAQ）被漏标，可运行 `python -m scripts.audit_eval_labels --run-id <run_id>` 做内容核验；确认后加 `--apply` 写回，脚本会记录审计日志

## 三、支持格式

评测页支持**多文件批量导入**：可一次选择多个 JSONL / JSON / CSV 文件，也可直接拖拽文件到导入区，或粘贴文本。系统会先解析并展示预览（有效条数、解析失败行号），确认后再入库。

### JSONL（推荐）
每行一个 JSON 对象，适合流式与大文件，解析失败的行会被报告。

```json
{"query":"如何办理退费？","relevant":["退费政策文档"],"gt_answer":"请到前台提交退费申请，3-5个工作日到账。","gt_keywords":["前台","退费申请","3-5个工作日"],"query_type":"policy","difficulty":"normal","notes":"政策类标准用例","source":"batch-2026-06"}
{"query":"Python 课每次消耗几课时？","relevant":["课时包说明"],"query_type":"fact","difficulty":"easy"}
```

### JSON 数组
整体为数组，元素结构同上。

```json
[
  {"query":"如何办理退费？","relevant":["退费政策文档"],"query_type":"policy"},
  {"query":"Python 课每次消耗几课时？","relevant":["课时包说明"],"query_type":"fact"}
]
```

### CSV
首行表头，逗号分隔；文本含逗号用双引号包裹；多值字段用 `;` 分隔。

```text
query,relevant,gt_answer,gt_keywords,query_type,difficulty,notes,source
"如何办理退费？","退费政策文档","请到前台提交退费申请","前台;退费申请;3-5个工作日","policy","normal","政策类标准用例","batch-2026-06"
```

## 四、校验规则

1. `query` 必须非空；空行自动跳过
2. `relevant` 中不存在的标题不报错，但会导致命中类指标失真
3. 单次导入上限 **500 条**，超出请分批；支持多文件合并计数
4. 导入**只追加、不覆盖**；默认按 `query`（忽略大小写与首尾空格）**跳过重复**，可在导入区关闭该开关
5. `query_type` / `difficulty` 非法值按默认值处理
6. 导入结果会给出成功/跳过/失败计数；解析失败与字段校验失败会按行号列出，修正后可重导
7. **批次命名（`source`）只是来源标记**，不会改变评测逻辑；同一评测集内所有用例会一起参与运行。不同批次名不会自动分组或隔离
8. 关闭「跳过重复 query」时，重复用例会重复计入指标；建议保持默认开启，或导入前自行去重

## 五、合规与安全要求（导入前必读）

1. **脱敏**：`query`、`gt_answer`、`notes` 不得含真实学员姓名、手机号、身份证号、家长联系方式、订单号、教师隐私；使用占位符（如「学员A」「教师B」）或哈希
2. **版权**：`relevant` 必须是本系统已接入的知识资产，不得导入第三方受版权保护的全文作为标准答案
3. **最小必要**：仅导入评测所需字段，不要整表导入业务库原始记录
4. **审计**：每次导入写入审计日志（操作者、数量、时间），请保留清洗脚本与原始数据以便追溯
5. **可回滚**：导入前保留原始文件与批次号，异常时按 `source` 定位并清理

## 六、指标口径

| 指标 | 含义 | 依赖字段 |
| --- | --- | --- |
| hit@k | 前 k 条召回是否命中任一相关文档 | `relevant` |
| MRR | 首个相关文档排名的倒数均值 | `relevant` |
| Context Precision@k | 前 k 条中相关文档占比（文档级上下文精确率） | `relevant` |
| Context Recall@k | 前 k 条覆盖的相关文档比例（文档级上下文召回率） | `relevant` |
| nDCG@k | 考虑排序位置的相关性增益 | `relevant` |
| 检索异常数 | 检索链路报错/超时的用例数，**不进入指标分母**，单独展示 | 运行环境 |
| 关键用例切片 | `business_criticality=critical` 的用例单独汇总，不被平均值稀释 | `business_criticality` |
| 冻结集切片 | `split=frozen` 的用例单独汇总，用于阶段验收 | `split` |
| 关键词命中 | 回答覆盖标准答案关键词的比例（已做全半角/空白/标点归一化） | `gt_keywords` |
| 引用覆盖率 | 未拒答回答中带有效来源编号（如 `[1]`）的比例 | 运行环境 |
| 无效引用率 | 引用了不存在的片段编号（超出上下文范围）的比例 | 运行环境 |
| 无依据回答率 | 未拒答但裁判忠实度 < 3 分的回答占比，**企业验收优先关注** | `gt_answer`（可空） |
| 答案正确性 | 裁判对照标准答案判断事实一致性（0-5） | `gt_answer` |
| 裁判评分 | LLM 按忠实度/相关性/完整性/逻辑性打分 | `gt_answer` |

## 七、验收闸门（回滚策略）

每次评测运行完成后，自动做闸门判断（判断结果在 `gate` 字段，前端详情页会展示）：

| 条件 | 阈值 | 说明 |
|---|---|---|
| 冻结集 hit@3 下降 | ≤ 2pp | 与上一次完成运行对比；下降超阈值判为回退 |
| 关键用例 hit@3 下降 | ≤ 2pp | 业务关键问题回退优先级最高 |
| 无依据回答率 | ≤ 5% | 未拒答且忠实度<3 的回答占比 |
| 检索异常率 | ≤ 0.1% | 检索链路报错不应进入质量指标分母 |
| 裁判-人工一致性 Kappa | ≥ 0.6（样本 ≥ 10 对） | 自动评测结论是否可信；不足样本时跳过 |

闸门结果：`pass` / `fail` / `skip`（未建冻结集或关键用例时跳过）。`fail` 时应拒绝上线并回滚到上一个闸门通过的配置版本。

> 没有 `split=frozen` 的用例时闸门跳过：先把至少 20% 的关键用例标为冻结集，再把闸门作为上线的强制条件。

## 八、裁判人机一致性校准（Kappa）

LLM 裁判的分数只有与人工复核高度一致时才可作为上线依据。评测页逐条结果支持「人工复核」打分（0-5）：

1. 在每条结果上点「评分」，填入 0-5 分与裁判名；
2. 系统把人工分与该条 `correctness` 分配对，用 **二次加权 Cohen's Kappa**（`evals/metrics.py: cohen_kappa`）计算一致性；
3. 当样本 ≥ 10 对且 Kappa < 0.6 时，闸门判 fail，自动评测结论不可信；
4. 详情页展示 Kappa、平均绝对差、bias（LLM 是否系统性偏高）。

> 二次加权对大偏差惩罚更重，更贴近「严重错误」的业务含义。Kappa ≥ 0.6 为 substantial agreement，通常作为企业上线门槛。

> 未提供 `relevant` 的用例不参与命中类指标；未提供 `gt_keywords` / `gt_answer` 的用例不参与对应质量指标。
>
> **检索异常与漏召回严格分开**：检索服务报错/超时的用例计入「检索异常数」，不进入 hit@k 等指标分母；只有成功执行（含成功返回空结果）的用例才参与质量统计。看到指标下降时，先确认异常数为 0，再判断是效果问题。
>
> **运行快照**：每次运行会冻结检索配置、集合名（Embedding 指纹）、分块参数、评测集内容哈希、生成/裁判模型与配置版本。历史运行可在详情中追溯；两次运行快照不一致时，delta 不能直接当作优化效果解读。
>
> 当前 Context Precision / Context Recall 是**文档级**指标，不是 RAGAS 的 chunk 级指标。若要做 chunk 级评测，需要把 `relevant` 升级为「相关分片 ID/文本片段」，并额外调用裁判模型逐段判断，成本与标注工作量都会显著增加；当前阶段建议先把文档级指标与答案正确性跑稳。

## 九、评测成本

评测运行产生的 LLM 调用（生成回答、裁判打分）归因到「用量与成本」模块 `rag_eval`，可在用量看板按模块筛选与对账。答案质量评测每个用例至少产生 **2 次** LLM 调用（生成 + 裁判），且两个模型分别按各自价格计费；大规模评测前建议先用小样本估算单次成本。

## 十、常见问题

- **导入成功但 hit@k 全为 0**：多为 `relevant` 标题与知识库标题不一致，核对后重导
- **CSV 解析错列**：文本含逗号未加双引号，或多值字段未用 `;` 分隔
- **超出上限**：单批 > 500 条被拒，请拆分批次并保留 `source`
- **评测成本偏高**：减少裁判调用或缩小样本，关注 `rag_eval` 模块耗费
- **批次命名不同有影响吗**：没有功能影响；`source` 只是来源标记，所有批次仍一起参与评测。重复 query 默认会被跳过
- **多文件导入顺序**：按选择/拖拽顺序合并解析；同一批次内重复 query 只保留第一条
- **提示“模型配置不属于评测运行 owner”**：生成/评测模型必须属于评测集 `owner_id`（未填时为当前账号），请切换到对应账号配置模型，或清空 `owner_id`
- **提示“生成模型与评测模型不能使用同一个模型”**：请选择不同模型；即使两个配置指向同一模型名也会被拒绝
