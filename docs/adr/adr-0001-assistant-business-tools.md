# ADR-0001：智能助手接入业务数据 —— 本地工具（Skill）层

- 状态：已采纳
- 日期：2026-06-16
- 关联：Agent 工作台 / 智能助手（`assistant`）、`app/services/agent_tools.py`

## 背景（Context）

智能助手（Agent 工作台的 `assistant`）此前只有两条"知识"来源：

1. **RAG**：上传的知识库文档检索（制度/流程/文化）；
2. **长期记忆**：会话中沉淀的偏好与事实。

它对**结构化业务数据一无所知**——排课与考勤、学员评估报告、教师教学数据、
班级与学员名单、课时预警等，都只能让用户自己去各业务模块翻。用户明确希望：
"让这个 Agent 能够知道排课考勤情况、学员评估报告、教师的各项数据等业务。"

约束：
- 现有对话走 SSE 流式（`llm.stream_text`），改动必须不破坏流式体验；
- 首字延迟敏感（此前已因"打招呼也检索"被投诉）；
- 数据必须**按当前用户权限/范围**返回，绝不能越权看到他人数据；
- 模型可切换（DeepSeek / OpenAI 兼容），不能依赖某家专有特性。

## 决策（Decision）

引入一层**只读业务工具（Skill）**，并在智能助手回答前做一次**工具规划 + 执行 + 注入**：

1. **工具注册表**（`agent_tools.py`）：每个工具声明 `name / description / 参数 JSON-Schema /
   处理函数`。全部为**只读**查询，按 `db + 当前 user` 作用域执行。
2. **规划**：用一次**非流式**的 function-calling 调用（LangChain `bind_tools`），
   让模型从问题里挑出要调用的工具与参数；**先用关键词启发式门控**，非业务问题（寒暄、纯知识库问答）
   直接跳过规划，避免无谓的一次 LLM 往返。
3. **执行 + 注入**：并发/顺序执行选中的工具，把结果整理成 `【业务数据】` 文本块，
   与 RAG 块、记忆块一并注入最终流式回答的 prompt。
4. **范围**：教师仅见本人数据；管理员/教务可见全局聚合。工具内部强制 scope，不信任模型传参。

示例工具：`my_schedule_overview`（我的排课与考勤）、`my_teaching_stats`（我的教学数据）、
`list_my_classes`（我的班级）、`student_progress`（某学员学习情况）、`student_evaluations`（学员评估报告）。

## 理由（Rationale）

- **不破坏流式**：规划是单独一次非流式调用，最终回答仍走原有 SSE 流，前端协议零改动。
- **延迟可控**：关键词门控让绝大多数非业务消息不触发规划；业务问题多一次快速调用是可接受的。
- **权限安全**：工具在服务端按 `user` 作用域取数，模型只能选"调哪个工具/给什么参数"，
  无法构造越权查询。
- **可扩展**：新增一项业务能力 = 注册一个工具函数，无需改动对话主流程，测试友好。
- **模型无关**：只依赖 OpenAI 兼容的 function-calling，DeepSeek / OpenAI 均支持。

## 备选方案（Alternatives considered）

- **全量预取**：每次对话把所有业务数据塞进 prompt。否决——token 爆炸、延迟高、泄露面大。
- **纯 RAG**：把业务数据当文档灌进向量库。否决——结构化数据更新频繁、需精确口径，RAG 不适合。
- **完整工具循环（多轮 ReAct）**：让模型连续多轮调用工具。暂缓——实现复杂、延迟不可控；
  当前"规划一次 → 执行 → 注入"已覆盖大部分问答场景，后续可平滑升级。

## 后果（Consequences）

- 正向：智能助手能基于真实业务数据回答，且不越权、不破坏流式、易扩展。
- 代价：业务问题会多一次非流式 LLM 规划调用（约几百毫秒）；规划失败时静默降级为纯 RAG 回答。
- 后续：若需要多跳查询或写操作（如"帮我把 X 排进课表"），再演进到多轮工具循环 + 写工具（需二次确认）。
